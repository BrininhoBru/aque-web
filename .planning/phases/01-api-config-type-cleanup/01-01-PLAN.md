| `environment` | exported const | `src/environments/environment.ts` | `{ apiBaseUrl: string }`, value `'/api'` (dev proxy target, see `proxy.conf.json`) |

No interface wrapper is created for the environment object: `npm run build` defaults to the production configuration, which compiles `environment.prod.ts` in place of `environment.ts`, so any shape drift between the two files breaks the build at every consumer. Plans 01-02 (six remaining services and three specs) and Phase 3 (new service specs) both consume the `environment` const above. Do not rename the export or add members without updating them.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser SPA -> `aque-backend` REST API | Every request crosses here carrying the `Authorization: Bearer` header injected by `authInterceptor`. This plan makes the base value a single high-leverage input to that boundary for every call site that later adopts it. |
| Build pipeline -> shipped bundle | `angular.json` `fileReplacements` selects which config module is compiled into the artifact deployed to the Pi. Anything placed in an environment file is public in the shipped JS. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | `src/environments/environment.ts` / `environment.prod.ts` | high | mitigate | If `apiBaseUrl` were resolvable at runtime from untrusted input (a `window.__env` global, a query parameter, a `localStorage` key), an attacker could redirect every authenticated request — and the bearer token with it — to a host they control. Mitigated by construction: both files export a plain string literal and nothing else, selected at **build time only** via Angular's `fileReplacements`. Task 1's acceptance criteria enforce this with a negative grep for `window`, `localStorage`, `sessionStorage`, `document`, `location` and `process.env` across `src/environments/*.ts`. |
| T-01-02 | Information Disclosure | environment files | medium | mitigate | Environment files are a common place for API keys to accumulate; everything in them ships in the public bundle. Mitigated by scope: the object has exactly one member, `apiBaseUrl`, holding a same-origin relative path. Task 1's action forbids secrets, tokens and keys explicitly. Re-check this at any future edit to these files. |
| T-01-03 | Spoofing | `auth.service.ts` login call | low | accept | The login endpoint URL construction changes but the request body, credential handling, JWT storage (`aque_token` in `localStorage`) and the `authInterceptor` chain are untouched. The pre-existing localStorage-JWT risk is a recorded, accepted decision (PROJECT.md / CONCERNS.md) and is explicitly out of scope for this milestone (REQUIREMENTS.md "Out of Scope"). |
| T-01-SC | Tampering | npm installs | high | accept | No package-manager install task exists in this plan — no dependency is added, removed or upgraded, so the supply-chain surface is unchanged and no package legitimacy audit is required. Enforced by acceptance gate: `git diff --exit-code package.json package-lock.json` must exit 0 (see `<verification>`). If a task turns out to need a new dependency, stop and route back to planning for a legitimacy audit rather than installing inline. |

ASVS level 1, block-on threshold `high`. T-01-01 is the one `high` threat carrying a mitigation, and its mitigation is enforced by an automated acceptance criterion in Task 1. T-01-SC is `high` by category but its disposition is `accept` on the grounds that the activity does not occur in this plan, with an automated gate proving it.
